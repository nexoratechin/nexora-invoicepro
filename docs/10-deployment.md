# Stage 8 - Deployment runbook

Everything here is prepared. Nothing is deployed, because that needs accounts and credentials that belong to Nexora Technologies.

Three pieces:

1. MongoDB Atlas, the database.
2. Render, the API.
3. Vercel, the web app.

The mobile app is built with EAS and is covered at the end.

## 0. Before you start

You need:

- A MongoDB Atlas account (free tier is enough).
- A Render account connected to the GitHub repository.
- A Vercel account connected to the same repository.
- Access to `github.com/nexoratechin/nexora-invoicepro`.

Generate the two secrets once and keep them somewhere safe:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

## 1. MongoDB Atlas

1. Create a free M0 cluster. Region: Mumbai (`ap-south-1`) if offered, otherwise Singapore.
2. Database Access, add a user with password authentication. Use a long random password. This user only needs `readWrite` on one database.
3. Network Access, add `0.0.0.0/0`. Render's free tier has no static egress IP, so a narrower allowlist means chasing changing IPs. The database user password is the control that matters.
4. Take the connection string from Connect, Drivers. It looks like:

```
mongodb+srv://nexora_app:PASSWORD@cluster0.xxxxx.mongodb.net/nexora_invoicepro?retryWrites=true&w=majority
```

The database name goes before the `?`. Create it on first write.

Atlas `srv` strings need DNS SRV lookups. Render supports them. If a connection hangs, check the password is URL encoded (`@` becomes `%40`).

## 2. Render, the API

A Blueprint file is in the repo: `render.yaml`.

1. Render dashboard, New, Blueprint, pick the repository. Render reads `render.yaml`.
2. It asks for the two secrets marked `sync: false`:

| Variable | Value |
| --- | --- |
| `MONGODB_URI` | the Atlas string from step 1 |
| `WEB_ORIGIN` | the Vercel URL, filled in after step 3. Comma separated if you have more than one, for example `https://nexora-invoicepro.vercel.app,https://app.nexoratechnologies.in` |

`JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are generated by Render and never leave it.

The build runs `npm ci && npm run build -w @nexora/server`. The start command is `node server/dist/index.js`. The health check is `GET /health`, so a boot that cannot reach MongoDB never goes live.

First boot builds shared, then the server, then connects. Expect about two minutes.

Note the URL: `https://nexora-invoicepro-api.onrender.com`.

Free instances sleep after 15 minutes. The first request then takes 20 to 40 seconds. `.github/workflows/keepalive.yml` pings it every 14 minutes; set a repository variable `PROD_API_URL` to the API URL to turn it on. Actions scheduled workflows are best effort and can be delayed, so treat this as a nicety, not a guarantee.

## 3. Vercel, the web app

1. Vercel, Add New Project, import the repository.
2. Framework preset: Vite. Root directory: the repository root, not `apps/web`. The `vercel.json` in the root already points the build at the workspace.
3. Environment variable:

| Variable | Value |
| --- | --- |
| `VITE_API_URL` | `https://nexora-invoicepro-api.onrender.com/api/v1` |

4. Deploy.

`vercel.json` handles the SPA rewrite (deep links like `/invoices/abc` must serve `index.html`), long lived caching for hashed assets, and four security headers.

Vite inlines `VITE_API_URL` at build time. Changing it needs a redeploy, not just an env var edit.

## 4. Close the loop

1. Copy the Vercel URL into Render's `WEB_ORIGIN` and let it redeploy. Until you do, the browser blocks every request with a CORS error.
2. Seed the demo data against Atlas, from your machine:

```bash
cd server
MONGODB_URI="mongodb+srv://..." JWT_ACCESS_SECRET="..." JWT_REFRESH_SECRET="..." npm run seed
```

The seed refuses to run with `NODE_ENV=production`. Leave it unset for this one command, or run it from a machine where `NODE_ENV` is not set. It writes 6 customers, 8 products and 12 invoices to the Atlas database.

3. Run the smoke test:

```bash
node scripts/smoke.mjs https://nexora-invoicepro-api.onrender.com
```

It checks health, database readiness, demo sign in, dashboard, invoice list, invoice detail, the PDF magic bytes, and that an anonymous request gets 401. Exit code 1 on the first failure, so it also works as a CI step after deploy.

4. Open the Vercel URL, sign in with `demo@nexora.test` / `nexora-demo-password`, open an invoice, download the PDF.

## Cookies and CORS in production

The web app and the API live on different registrable domains, so the browser treats their cookies as cross-site. That drove two decisions:

- The refresh cookie is set with `SameSite=None; Secure` when `NODE_ENV=production`, because `Strict` would simply never be sent and every page load would log the user out. In development it stays `Strict`.
- Because `None` allows any site to make the request, `POST /auth/refresh` and `POST /auth/logout` reject a request whose `Origin` is not in `WEB_ORIGIN`. That is tested.

CORS allows exactly the origins in `WEB_ORIGIN`, with credentials. The API never uses a wildcard.

A custom domain pair such as `app.nexoratechnologies.in` and `api.nexoratechnologies.in` is same-site, so you could switch the cookie back to `Strict`. Worth doing after the portfolio review.

## Mobile builds

```bash
cd apps/mobile
npx eas build --platform android --profile preview
```

Set `EXPO_PUBLIC_API_URL` to the deployed API before building. The value is inlined into the bundle, so a device build cannot point at localhost.

iOS needs an Apple Developer account and EAS credentials. Not done here, and not claimed.

## Rolling back

Render keeps previous deploys: Deploys, pick the last good one, Redeploy.
Vercel: Deployments, promote a previous deployment.

Neither rollback covers the database. A migration script that breaks data has to be undone by hand, so back up before running one (`mongodump` against Atlas, or a snapshot on a paid tier).

## What is not automated

- No infrastructure as code beyond `render.yaml`.
- No staging environment. The free tiers allow one of each; a second Render service and a second Atlas database would give you staging if you want to pay for it later.
- No automated post-deploy smoke in the pipeline. The script is ready for it, but it needs the demo account to exist on the deployed database.
- No custom domain or TLS setup. Both hosts provide TLS on their own domains.
